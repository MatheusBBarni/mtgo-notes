# ADR-002: Require Policy-Bounded Automatic Match Context

## Status

Superseded on `feat/winui-rewrite` by [ADR-009](../../winui-rewrite/adrs/adr-009.md)

## Date

2026-07-28

## Context

The initial idea used manual opponent identification to minimize MTGO policy risk. During PRD clarification, the user identified MTGBot's streamer workflow as the target experience: when a round begins, the player should see the current opponent and the opponent's most recent public deck for that format.

Manual entry alone would not satisfy that experience. At the same time, the MTGO EULA gives Daybreak broad discretion over third-party programs that affect gameplay or collect information from or through the game. MTGBot publicly documents live tournament status and recent-deck lookup, but it does not document a general integration API or a public match-ended event.

## Decision

V1 requires automatic opponent and match-state detection through at least one officially approved or user-authorized source. Manual entry is a runtime fallback, not a substitute for completing the automatic capability.

The product will enforce these rules:

- It will not inspect MTGO processes, memory, files, logs, or network traffic unless Daybreak explicitly approves that access.
- A detected opponent must be confirmed before creating or updating a persistent profile. Uncertain detection falls back to correction or manual entry.
- Match phases will update automatically when the approved source provides sufficient evidence. Users can correct the phase manually. Uncertainty fails closed by hiding historical information during possible gameplay.
- A confirmed new opponent automatically completes the prior active encounter, preserves unconfirmed fields as unconfirmed, starts the new encounter, and offers undo or reopen.
- If no confident match-end signal arrives, the product prompts for confirmation. An ignored prompt leaves the encounter incomplete.
- Public deck history refreshes at each confirmed encounter. The lookup uses the current format, requires onboarding consent, and can be disabled.
- A public deck result must be confirmed before it becomes a dated snapshot. The snapshot retains its event, publication date, provider, and source link.
- Public deck data and user-authored deck observations remain separate when they conflict.
- Unsupported formats, provider outages, and offline use preserve the full local note workflow while omitting unavailable enrichment.

## Alternatives Considered

### Alternative 1: Manual Opponent and Phase Entry

- **Description**: Require the player to identify every opponent and change every match phase manually.
- **Pros**: Lowest integration and policy risk; fully offline.
- **Cons**: Fails to deliver the MTGBot-like experience; increases clock pressure and duplicate profiles.
- **Why rejected**: The user made automatic context a V1 release requirement.

### Alternative 2: Unofficial Direct MTGO Inspection

- **Description**: Use community tooling to inspect client state without explicit Daybreak approval.
- **Pros**: Could provide rich, immediate opponent and lifecycle events.
- **Cons**: Creates account-enforcement and policy risk; expands the sensitive integration surface.
- **Why rejected**: The user selected an approved or user-authorized source boundary.

### Alternative 3: Streamer-Only MTGBot Integration

- **Description**: Import context only from a Twitch or MTGBot-enabled stream.
- **Pros**: Mirrors an established workflow; may avoid direct MTGO inspection.
- **Cons**: Excludes non-streamers and turns a reference experience into a product dependency.
- **Why rejected**: V1 explicitly serves any individual MTGO player, not streamers first.

## Consequences

### Positive

- Delivers the low-friction context experience that motivated the product.
- Keeps automatic data attributable, correctable, and distinct from personal observations.
- Preserves local capture and recall during outages or unsupported formats.
- Creates explicit user-visible failure and correction paths.

### Negative

- V1 depends on finding and validating at least one acceptable context source.
- Public data can be stale, missing, incorrectly matched, or rate-limited.
- Automatic lifecycle signals remain probabilistic and require manual correction paths.
- External lookups disclose confirmed handles and formats after user consent.

### Risks

- **Provider unavailable or undocumented**: Validate provider access before committing the TechSpec; retain manual fallback.
- **Wrong opponent association**: Require confirmation before persistence and support reversible profile merges.
- **False match-end signal**: Offer undo or reopen and keep uncertain fields unconfirmed.
- **Policy interpretation changes**: Keep integrations replaceable, disclose their source, and provide an immediate disable control.
- **Stale public deck**: Show the date, format, event, and source; never label it as the current deck.

## Implementation Notes

The TechSpec must select the automatic context provider and document why its access is officially approved or user-authorized. The product contract is provider-independent and must not assume that MTGBot exposes a reusable API.
