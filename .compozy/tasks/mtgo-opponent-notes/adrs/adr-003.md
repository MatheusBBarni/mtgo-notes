# ADR-003: Keep the Notebook Local While Supporting Recovery and Text Export

## Status

Accepted

## Date

2026-07-28

## Context

The notebook accumulates private opponent handles, personal observations, public deck snapshots, and encounter history. Long-term local ownership is part of the product's value, but device loss, corruption, and vendor lock-in would make the accumulated history fragile.

The idea-stage scope allowed encrypted backup and restore while excluding readable export. During PRD clarification, the user explicitly added a V1 export button that produces a human-readable text file. This decision supersedes ADR-001 only where ADR-001 deferred readable export.

## Decision

V1 will keep the canonical notebook on the player's device and will not require an account or cloud synchronization.

The product will enforce these rules:

- Notebook history remains until the player deletes it.
- Notes are editable while retaining encounter timestamps and a visible edited marker.
- Deletion provides a short undo opportunity. Permanent deletion of an encounter, opponent, or the entire notebook requires confirmation.
- Network telemetry is absent. Diagnostics remain local and can be included only in an explicit user-created support bundle that excludes opponent handles, note content, and public lookup results.
- Encrypted backup and restore are explicit user actions. A backup must be validated and previewed before restore.
- Restore offers merge or replace. The current notebook is preserved for rollback before either operation.
- Merge skips exact duplicates, combines matching profiles through the reversible alias rules, and preserves both versions of genuine conflicts for later resolution.
- Backup passphrases cannot be recovered. The product must disclose that consequence before backup creation.
- A text export can contain either the complete notebook or one selected opponent, organized by encounter with timestamps, provenance, and source labels.
- Text export is unencrypted, requires a privacy warning, and is one-way. It cannot be imported as a restoration format.
- Cloud accounts, cloud sync, public sharing, and crowdsourced opponent profiles remain out of scope.

## Alternatives Considered

### Alternative 1: Encrypted Backup Without Readable Export

- **Description**: Preserve the idea-stage boundary and allow only application-managed encrypted recovery files.
- **Pros**: Minimizes disclosure and parsing ambiguity; reduces the portable dossier surface.
- **Cons**: Prevents human-readable ownership and creates application lock-in.
- **Why rejected**: The user explicitly requires a V1 text-export button.

### Alternative 2: Cloud Account and Synchronization

- **Description**: Store or synchronize notebook data through an online account.
- **Pros**: Simplifies multi-device continuity and account-based recovery.
- **Cons**: Expands privacy, security, operational, and moderation obligations.
- **Why rejected**: V1 is explicitly local-only and account-free.

### Alternative 3: Round-Trip Text Import and Export

- **Description**: Make the human-readable text format sufficient for reconstructing the notebook.
- **Pros**: Maximizes portability and inspectability.
- **Cons**: Creates ambiguous conflict, provenance, validation, and corruption behavior.
- **Why rejected**: Encrypted backups are the supported restoration format; text export exists for reading and ownership.

## Consequences

### Positive

- Players retain durable ownership of accumulated history.
- Recovery preserves privacy without requiring a cloud service.
- Human-readable export reduces lock-in.
- Conflict preservation avoids silent data loss.
- No telemetry prevents opponent and note data from leaving the device for analytics.

### Negative

- Forgotten backup passphrases make those backup files unrecoverable.
- Text exports can be copied or exposed outside protected storage.
- Merge and rollback behavior increase the recovery product surface.
- Local-only storage does not provide automatic multi-device continuity.

### Risks

- **Sensitive text export**: Require an explicit unencrypted-file warning and user-selected destination.
- **Restore corruption or incompatibility**: Validate before applying and preserve a rollback copy.
- **Duplicate profiles after merge**: Apply the reversible canonical-handle and alias rules.
- **Diagnostic leakage**: Exclude handles, content, and public results from support bundles.
- **Unrecoverable backup**: Confirm passphrase-loss consequences before creation.

## Implementation Notes

The user selected SQLite as the V1 local persistence constraint. The TechSpec must define the database, local protection, backup container, atomic restore, rollback, and text rendering formats without weakening the product rules above.
