# ADR-007: Ship an Immutable Versioned Local Archetype Classifier

## Status

Accepted

## Date

2026-07-28

## Context

The user added local archetype classification during technical clarification and supplied an Archetype Cleaner reference showing format-specific signature definitions and a k-nearest-neighbors fallback. Players should see useful, explainable archetypes for complete decks, but they must not edit classifier rules inside the application. Definitions and training data will evolve with newer releases.

The classifier must remain offline, avoid inference from partial in-game observations, retain provenance, and update historical results without destroying earlier interpretations.

## Decision

Bundle immutable, signed, versioned classifier assets with each application release.

- Each asset bundle declares schema version, classifier version, effective date, supported formats, ordered archetype definitions, confidence thresholds, and a labeled deck corpus.
- Signature definitions support `minCopies`, `exactCopies`, and `strictMode`. The engine normalizes a complete deck into a format-aware card-count vector, evaluates signature rules in stable declared order, and records the decisive rule.
- If no signature rule matches, the engine runs local k-nearest-neighbors over the bundled corpus using a documented weighted card-vector distance. Stable neighbor and archetype ordering resolves ties. Scores below the bundled threshold return `Unclassified`.
- Automatic classification accepts only complete confirmed public decklists or complete user-entered decklists. Partial observed or suspected cards never enter the engine.
- Classification runs are append-only and unique by `(deck_revision_id, classifier_version)`. They record method, result, confidence, explanation, and asset digest.
- On update, validate the new asset signature, schema, digest, and compatibility before activation. A resumable low-priority job appends new runs for stored complete deck revisions. Prior runs remain queryable; the newest successful compatible run is displayed by default.
- No configuration or catalog-management screen ships in V1. Deck details expose result, method, classifier version, confidence, matched signatures or nearest neighbors, and separate provider labels.

## Alternatives Considered

### Alternative 1: Runtime YAML Editor

- **Description**: Let players create, validate, activate, and delete signature definitions in the app.
- **Pros**: Fast community tuning and user control.
- **Cons**: Creates unsafe migrations, support burden, inconsistent classifications, and a large editor/testing surface.
- **Why rejected**: The user explicitly chose app-owned definitions updated through releases.

### Alternative 2: Signature Rules Only

- **Description**: Return `Unclassified` whenever no deterministic signature matches.
- **Pros**: Simple, fast, and maximally explainable.
- **Cons**: Lower coverage for complete decks that lack the selected signatures.
- **Why rejected**: The user selected the reference's local k-nearest-neighbors fallback.

### Alternative 3: Classify Partial Observations

- **Description**: Infer a live archetype from cards observed during a match.
- **Pros**: Provides immediate current-match categorization.
- **Cons**: Weak evidence can look authoritative and expands strategic assistance during gameplay.
- **Why rejected**: The user selected complete-deck classification only.

## Consequences

### Positive

- Classification is offline, reproducible, explainable, and versioned.
- Release updates can improve historical classifications without rewriting past runs.
- Provider labels and local results can disagree without losing provenance.

### Negative

- Releases must maintain classifier assets and a labeled corpus.
- Background reclassification adds CPU and storage work after updates.
- No runtime editor means corrections require a new release.

### Risks

- **Bad asset release**: Validate before activation and retain the last valid bundle.
- **Classification drift**: Preserve every run and surface the version.
- **Resource contention**: Pause jobs while capture, backup, restore, or MTGO foreground activity is detected.
- **Corpus licensing**: Ship only deck data the project has rights to redistribute and record its source manifest.

## Implementation Notes

Treat classifier output as derived data, never as the source deck identity. The engine is a pure Rust component with golden asset fixtures and cross-version determinism tests. Asset files live under the signed application resource bundle; the database stores only their digest and derived run records.
