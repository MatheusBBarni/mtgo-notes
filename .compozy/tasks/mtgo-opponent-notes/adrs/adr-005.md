# ADR-005: Detect Visible MTGO Context Through UI Automation and OCR

## Status

Superseded on `feat/winui-rewrite` by [ADR-009](../../winui-rewrite/adrs/adr-009.md). UIA/OCR remains a fallback, not the primary source.

## Date

2026-07-28

## Context

ADR-002 requires an automatic opponent and match-state provider without inspecting MTGO process state, memory, files, logs, or network traffic. Daybreak's Census API is an approved MTGO data service, but its public documentation does not establish a live opponent or match-phase feed. MTGBot proves that the desired experience exists but publishes no reusable integration API.

The selected provider must read only information already visible to the player, require explicit consent, tolerate MTGO UI changes, and fail closed whenever gameplay might be active.

## Decision

Ship a Windows on-screen context provider in the Rust host.

- Let the user select the visible MTGO top-level window and track its window handle, class, and visible title without opening or inspecting the process.
- Read visible accessible names, labels, and state through Windows UI Automation first.
- When required fields are unavailable, capture only user-approved, versioned rectangular regions of the visible MTGO window and run the built-in Windows OCR engine.
- Normalize candidate handles and phase signals, attach source evidence and confidence, and pass them to a deterministic encounter state machine. OCR text and screenshots are ephemeral and never persisted or included in diagnostics.
- Require player confirmation before attaching an opponent to persistent history. An uncertain phase maps to `in_game_restricted`.
- Treat a newly confirmed different opponent as strong evidence that the previous match ended: complete the prior encounter and offer undo/reopen in one ordered transaction.
- If no confident end signal arrives, prompt for completion. Ignoring the prompt produces an incomplete encounter.
- Public-deck enrichment uses a separate provider contract. V1 targets official MTGO public decklists only after validating documented automated access. Without that validation, it opens the official player search for user-confirmed source selection and never silently scrapes a third-party site.

## Alternatives Considered

### Alternative 1: Wait for a Daybreak or MTGBot Live API

- **Description**: Block automatic detection until a documented live integration is granted.
- **Pros**: Clear authorization and structured events.
- **Cons**: No public live API is currently established and the V1 release gate would remain blocked indefinitely.
- **Why rejected**: Visible, user-authorized UI data can meet the selected boundary without direct client inspection.

### Alternative 2: Use Unofficial MTGO SDK or Log Parsing

- **Description**: Read client objects, memory, logs, or traffic through community tooling.
- **Pros**: Rich, precise opponent and lifecycle events.
- **Cons**: Violates ADR-002's selected policy boundary without explicit Daybreak approval.
- **Why rejected**: The product must not create account-enforcement risk through undocumented direct inspection.

### Alternative 3: OCR Every Frame

- **Description**: Continuously capture and OCR the entire MTGO window.
- **Pros**: Minimal dependency on accessibility metadata.
- **Cons**: High CPU use, more sensitive image handling, false positives, and unnecessary capture scope.
- **Why rejected**: UI Automation plus event-driven, cropped OCR minimizes data and resource use.

## Consequences

### Positive

- V1 can automatically detect visible opponent and phase context without touching hidden client state.
- The provider is replaceable and can coexist with a future approved structured API.
- Confidence and evidence make corrections and fail-closed behavior explicit.

### Negative

- MTGO UI changes can invalidate locators or capture regions.
- Windows OCR depends on installed language support.
- Match-end detection remains probabilistic.

### Risks

- **False identity**: Require confirmation and reuse aliases only after exact normalized matching.
- **False non-game phase**: Require corroborating evidence to leave the restricted state.
- **CPU spikes**: Debounce UIA events, rate-limit OCR, and pause capture when MTGO is minimized or absent.
- **Provider policy changes**: Expose immediate pause/disable controls and retain manual operation.

## Implementation Notes

The provider emits `ContextEvidence` records only into memory. A reducer orders signals by monotonic sequence and encounter generation. Tests use captured, redacted synthetic UIA trees and synthetic cropped images; no test depends on a live MTGO account. A packaged manual validation matrix remains required before release.
