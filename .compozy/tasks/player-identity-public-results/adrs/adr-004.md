# ADR-004: Use Dedicated Player Persistence and Trusted-Host Runtime

## Status

Accepted

## Date

2026-08-03

## Context

The existing repository models opponent profiles, encounters, public snapshots,
and deck revisions through required foreign keys and encounter-triggered services.
The Player workflow has different ownership, trigger, consent, replay, deletion,
and portability rules. Reusing opponent tables or renderer-built requests would
make those rules impossible to enforce without coupling unrelated workflows.

## Decision

Add a forward migration with dedicated Player identity, source consent, evidence,
card, selection revision, empty outcome, classification run, tombstone, and durable
operation-receipt tables. Implement a host-owned Player public-results runtime that
loads authoritative identity/consent/configuration, owns lookup sessions and
previews, enforces caller/phase/routes/limits, and emits bounded replacement views.
Only generic SQLCipher, operation, IPC, portability, browser-shell, classifier, and
React primitives may be reused.

## Alternatives Considered

### Alternative 1: Extend opponent profiles and public snapshots

- **Description**: Represent the local player as a special opponent profile and
  attach public evidence to existing encounter/deck tables.
- **Pros**: Fewer tables and apparent reuse of existing views.
- **Cons**: Requires fake encounter ownership, risks cross-workflow mutations, and
  cannot express Player-specific consent, deletion, or merge conflicts cleanly.
- **Why rejected**: It violates the approved bounded-context separation.

### Alternative 2: Let renderer state build provider requests

- **Description**: Accept nickname, URLs, scope, provenance, and consent state from
  the React surface.
- **Pros**: Less native orchestration and faster UI iteration.
- **Cons**: Makes disclosure-sensitive inputs attacker-controlled and weakens route,
  replay, fencing, and capability guarantees.
- **Why rejected**: The native host is the sole trusted authority for external side
  effects and durable evidence.

## Consequences

### Positive

- Player and opponent ownership remains mechanically enforceable.
- External access and evidence import fail closed at one trusted boundary.
- Portability, deletion, and replay rules can be tested independently.

### Negative

- The migration and repository gain several Player-specific tables and services.
- Generic infrastructure needs explicit extension points rather than automatic
  table discovery.

### Risks

- Cross-table drift could create orphaned data; foreign keys, transaction tests, and
  canonical archive ordering mitigate it.
- Runtime and durable state could leak content; schemas and diagnostics must use
  strict allowlists.

## Implementation Notes

Use migration version 3 after the existing v1/v2 chain. Keep session, preview,
audit, cooldown, and transient replay state in memory. Persist only the minimum
receipt needed for idempotent durable mutations or at-most-once browser handoff.
