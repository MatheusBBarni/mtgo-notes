# ADR-006: Keep Census Configuration Host-Only and Disabled by Default

## Status

Accepted

## Date

2026-08-03

## Context

Census requires an authorized Service ID and a current source contract, but its
published policy does not establish a safe redistributed-desktop credential model
or registered-ID quota for this product. Renderer configuration, plaintext settings,
or a bundled placeholder could accidentally enable requests or expose credentials.

## Decision

Implement Census behind a narrow adapter with `Disabled`, test-only `Synthetic`,
and host-only `Live` constructions. Production runtime starts disabled. A live
adapter can exist only when host-held reviewed configuration passes provider,
scope, disclosure, expiry, and credential validation. Renderer payloads cannot
construct or alter routes, scopes, credentials, or enablement. Missing or invalid
evidence means zero requests.

## Alternatives Considered

### Alternative 1: Store provider configuration in application settings

- **Description**: Let the renderer persist endpoint, scope, and Service ID.
- **Pros**: Easy configuration and testing.
- **Cons**: Exposes secrets, permits arbitrary endpoints, and makes stale or hostile
  renderer state authoritative.
- **Why rejected**: Provider authority must remain native and fail-closed.

### Alternative 2: Ship a placeholder or shared Service ID

- **Description**: Enable the adapter using `s:example` or a common embedded ID.
- **Pros**: Immediate live development path.
- **Cons**: Violates the reviewed production gate and may disclose or exhaust a
  shared credential.
- **Why rejected**: Synthetic fixtures provide implementation evidence without
  pretending production authorization exists.

## Consequences

### Positive

- An implemented adapter cannot accidentally become a live feature.
- Tests remain deterministic and transmit no real nickname or credential.
- Provider policy/configuration drift can disable access without data loss.

### Negative

- Live validation requires an external authorization/configuration process.
- Local implementation completion does not imply production availability.

### Risks

- A Service ID embedded in a desktop binary may still be extractable; the approved
  distributed-client use model must address custody before live enablement.

## Implementation Notes

Do not persist the Service ID in notebook tables, settings JSON, diagnostics,
backup, export, IPC, or attribution. The TechSpec treats exact live injection as an
external release concern until Daybreak's use model is approved.
