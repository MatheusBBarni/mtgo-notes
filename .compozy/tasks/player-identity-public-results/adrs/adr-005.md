# ADR-005: Persist Player Classification Runs Independently

## Status

Accepted

## Date

2026-08-03

## Context

The classifier engine accepts a complete deck and produces deterministic local
classification output, but existing `classification_runs` rows belong to opponent
`deck_revisions`. Complete official Player evidence may use the engine, while
reference-only or partial evidence may not. Sharing persistence would require a
polymorphic ownership migration across an already executed opponent workflow.

## Decision

Reuse the pure classifier engine and signed classifier assets at the complete-deck
input boundary, but store results in `player_classification_runs` linked only to a
Player evidence version. Preserve classifier version, digest, method, result,
confidence, and creation time using the same immutable provenance semantics. Never
create an opponent deck revision or classification row for Player evidence.

## Alternatives Considered

### Alternative 1: Generalize classification ownership polymorphically

- **Description**: Replace the current opponent foreign key with a shared subject
  type and subject ID.
- **Pros**: One classification-run table and common queries.
- **Cons**: Broad migration, weaker foreign-key guarantees, and regression risk for
  completed opponent behavior.
- **Why rejected**: V1 gains no user value from a cross-domain persistence refactor.

### Alternative 2: Copy Player evidence into opponent deck records

- **Description**: Create a synthetic opponent deck revision for classification.
- **Pros**: Reuses all current persistence unchanged.
- **Cons**: Falsifies ownership and may expose Player evidence through opponent UI,
  history, deletion, and portability paths.
- **Why rejected**: It directly violates the approved isolation boundary.

## Consequences

### Positive

- Existing classifier behavior and assets are reused without schema coupling.
- Player evidence retains correct ownership and independent lifecycle.
- Reference-only and unsupported data can remain honestly unclassified.

### Negative

- Classification result persistence and reclassification need a Player-specific
  adapter and queries.
- Some mapping code duplicates the opponent classification result shape.

### Risks

- Engine/result semantics could drift between owners; shared pure types and golden
  vectors mitigate drift while persistence remains separate.

## Implementation Notes

Queue classification only after an atomic import of complete, format-valid official
decklist evidence. Classification failure must not roll back the evidence import.
