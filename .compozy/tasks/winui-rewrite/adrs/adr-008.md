# ADR-008: Replace the Tauri Host with an Unpackaged WinUI 3 App

## Status

Accepted

## Date

2026-08-17

## Context

ADR-004 selected Tauri 2 so a React `DESIGN.md` UI could sit behind a Rust trusted host. That split is working for a notes-first companion that only reads the visible MTGO window.

The product direction has changed. Live match context will come from [MTGOSDK](https://github.com/videre-project/MTGOSDK), a .NET library that attaches to a running MTGO process. A sidecar was rejected: two runtimes, two installers, and a pipe in the middle of the encounter loop. The host language must be the same as the live client library.

The app remains Windows 10 22H2 / Windows 11 x64 only. Cross-platform is not a constraint.

## Decision

Rewrite the desktop host as an unpackaged Windows App SDK / WinUI 3 application in C# / .NET 10.

- One process owns shell, live attach, encounter reduction, disclosure, SQLCipher, and UI.
- The project is unpackaged (`<WindowsPackageType>None</WindowsPackageType>`) so the existing NSIS-style companion install can continue. MSIX is a later packaging option, not a rewrite prerequisite.
- UI is native WinUI 3 XAML. `DESIGN.md` is re-expressed as a WinUI resource dictionary. React / WebView2 / Tauri are not part of the rewrite target.
- The three surfaces remain separate windows: `main` (1200×800, min 960×680), `overlay` (360×220, always-on-top, click-through until expanded), `capture` (420×160, shortcut-activated).
- Overlay and capture cannot reach notebook, search, backup, or history services. They receive policy-filtered facades only. This replaces Tauri capability manifests.
- The existing Tauri / React / Rust tree stays on this branch as a frozen reference until WinUI parity is accepted. It is not compiled as part of the new app.

## Alternatives Considered

### Alternative 1: Keep Tauri and add a .NET sidecar

- **Description**: Leave the current host; stream `ContextEvidence` from a small MTGOSDK worker.
- **Pros**: Preserves the finished V1 host; smallest diff.
- **Cons**: Two processes, reconnect races, dual packaging, and a rejected product direction.
- **Why rejected**: Explicitly ruled out.

### Alternative 2: WinUI 3 shell with a WebView2 notebook

- **Description**: C# owns MTGOSDK and data; React keeps `DESIGN.md` in the main window.
- **Pros**: Reuses the current visual system.
- **Cons**: Rebuilds a capability bridge, keeps WebView2, and still rewrites the trusted core.
- **Why rejected**: The rewrite is a commitment to a native Windows companion, not another website-in-a-box.

### Alternative 3: WPF

- **Description**: Use WPF for the overlay HWND, which is historically easier for layered click-through.
- **Pros**: Mature layered-window story.
- **Cons**: Older stack; WinUI 3 is the current Windows App SDK UI. Overlay difficulty is a spike, not a reason to start on WPF.
- **Why rejected**: Spike WinUI 3 first. Revisit WPF only if the overlay kill-gate fails.

## Consequences

### Positive

- MTGOSDK, UIA, OCR, DPAPI, tray, and AppWindow live in one debugger.
- No IPC confused-deputy between webviews and the notebook.
- The product can grow Videre-like match chrome without a second architecture.

### Negative

- The current Tauri host, React UI, capability lint, and most of the test harness are thrown away after cutover.
- All UI and live-client work requires a Windows machine. macOS can only edit Core tests that do not touch WinRT.
- Click-through always-on-top overlays are not a first-class WinUI 3 feature and must be proven before the rewrite proceeds.

### Risks

- **Overlay input**: `OverlappedPresenter.IsAlwaysOnTop` is supported; click-through still needs `WS_EX_TRANSPARENT | WS_EX_LAYERED` on the HWND. If the spike cannot show, ignore clicks, then expand without stealing MTGO focus, stop and reconsider the shell.
- **Trusted UI**: XAML runs in-process. A view that bypasses `DisclosurePolicy` can leak history. Facades and tests must make that impossible from overlay/capture types.
- **Windows App SDK bootstrap**: unpackaged apps must initialize the runtime. The installer has to ship or detect that dependency the same way it currently bootstraps WebView2.
- **Lost V1 evidence**: packaged Windows UIA/OCR/updater evidence does not transfer. The rewrite needs its own Windows gate.

## Implementation Notes

See [the rewrite plan](../_plan.md). Do not delete `src/` or `src-tauri/` until the WinUI app reaches notebook parity and can open an existing SQLCipher database.
